# RORET union census (M11)

## Scope (read this first)

host-side census driven by fixture top-k ids with the real llama_roret_union_cache and the (ip, pass) keys the Inkling2 graph supplies to the MoE cache layer; NOT engine runtime traffic, NOT GPU residency, NOT wall-clock, NO speed claim

Standing rule: any speed number requires loopkit CycleAudit claim <= ci_low with repeats>=20 and loops=3.

Issue #4 (engine GPU bit-exact parity) was NO_GO at M11: no nvcc/GPU build was
available locally then. M18 later measured engine final-logits parity PASS-scoped
on Kaggle 2xT4; intermediate per-pass tensors remain NOT measured.

Issue #5 (T4 per-pass MoE traffic) remains NO_GO: on GGML_CUDA=OFF with
LLAMA_RORET_CPU_TEST=ON the scheduler never calls llama_moe_cache::copy(), so
the runtime counter table has zero per-pass rows locally. The counts below are
a host-side census, not those counters and not T4 traffic.

## Why this census exists

The Inkling2 graph passes `roret_il` (logical core layer ip) and `roret_pass`
(0..2) into `llm_graph_context::build_moe_ffn`, and llama-graph.cpp forwards
them into `llama_moe_cache_layer::roret_key`. The graph-side bookkeeping call
there has a nullptr cache/ids, so on the local CPU-test build no union rows are
created. This census supplies the missing evidence by replaying the real
runtime union-cache semantics with the real graph keys and the real top-k ids
from the deterministic seed-0 fixture. It changes no src/ file and touches no
graph node, router, logits or selected-expert tensor.

## What was measured

For every token (T=4) and every looped core layer (ip=6..17, 12 layers), for
passes 0,1,2 in order, using the ids in `dump['topk_ids']` with shape
[L=24][P=3][T=4][K=8] (the dump's real key name; task shorthand `topk` refers
to this same array):

1. On pass 0 only, `clear_layer(ip)` (fresh union per token, as the cache does).
2. `hit_rate({ip,pass}, ids, 8)` BEFORE `add()` -- earlier-pass residents only.
3. `add({ip,pass}, ids, 8)` on the real `llama_roret_union_cache` from
   `src/llama-roret.h`, followed by `residents(ip).size()` and
   `total_residents(ip)`.

Accumulated per (ip,pass): token count, registered id count, hit count before
add, adds that grew the union, and min/max/mean union size after add. Each
(ip,pass) row therefore has 4 tokens and 32 ids.

Assertions enforced by `assert()` in the test:
(a) pass-0 `hit_rate` is 0 for a fresh union (and residents-before is 0);
(b) every pass's union size is in [8,24] = [top_k, passes*top_k];
(c) pass-2 union size >= pass-1 union size >= pass-0 union size per layer and
    token (monotone);
(d) OFF loads = 3*8 = 24 per layer/token and ON loads = final union size,
    reported as COUNTS.

## Interpretation: this does NOT reproduce the probe union

The mean final union here is **20.333333**, far above the 8.25-11.58 mean union
reported by the 100k-token scalar probe in `tools/roret/KAGGLE_RESULTS.md` and
summarised in `tools/roret/TRAFFIC_REPORT.md`. It must not be read as
confirmation of that load-reduction precondition. The two are different
instruments: the probe sweeps a synthetic cross-loop message scale on 100k
tokens, while this census replays the seed-0 fixture's actual three-pass
top-k ids on only 4 tokens, whose per-pass sets largely disagree (pass-2
hits-before-add are 5-21 of 32 ids per layer). The fixture is a determinism and
wiring test vehicle, not a calibrated model of routing stability. No load
reduction, bandwidth saving, or speedup follows from these counts.

Two further scope notes. First, the keys used here are the `(ip, pass)` values
that `src/models/inkling2.cpp` supplies to `build_moe_ffn` and that
`src/llama-graph.cpp` forwards into `llama_moe_cache_layer::roret_key`; on the
local `GGML_CUDA=OFF` / `LLAMA_RORET_CPU_TEST=ON` build no copy callback fires,
so no runtime row exists to compare against. Second, the census clears the
union per token (max 24 ids), whereas a real `copy()` callback clears per
execution of its split (potentially a multi-token ubatch); the counts below are
therefore a per-token census, not an engine-side counter reading.

## OFF=24 vs ON=union counts

OFF loads three independent top-8 id sets per layer/token, so 3*8 = 24 count
units in every one of the 48 layer-token samples: total OFF = 1152.
ON loads one resident set of the final union size per layer/token: total
ON = 976, the sum of the 48 final union sizes. These are discrete load COUNTS
derived from the fixture ids and the real union cache; they are not bytes,
not device traffic, not bandwidth, and not time.
